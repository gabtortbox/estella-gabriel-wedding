# Before Sending Invitations

Local automated checks use fictional guests, not your real master. They cannot
prove Google permissions, mobile networks or the deployed versions work. Complete
these final real-service checks. No software can be guaranteed to have zero bugs.

## Setup And Link Stability

- [ ] The master Guestlist has final names, unique B groups, D categories and G
  intent. Every G = Yes row has a B and F. No real invitations have been sent yet.
- [ ] Update invitation codes ran successfully on the REAL master. G = No rows
  have blank A/B. H, I, J, K and all other source cells are unchanged.
- [ ] Everyone in one B group shares A. Groups 50 and 51 have different A codes.
  Blank G people do not appear online. Test codes are not real guest links.
- [ ] Run the menu a second time. Codes do not change. Insert/reorder whole rows
  in a trial and run again; the same groups keep the same links.
- [ ] Existing Apps Script deployment reports protocol 3 and configured true.
- [ ] GitHub Actions finished successfully on main; latest website is published.
- [ ] Delete any old public guestlist.json from GitHub; never upload real guest data.

## Fictional Guests On The Actual Deployment

Add two unmistakably fictional trial groups to Guestlist: one Family group of
2-3 people, one Friends group of 2. Give each a NEW unused B, G = Yes and I = No.
Use fake names only. Let A fill, then open the corresponding published links:
`https://gabtortbox.github.io/estella-gabriel-wedding/?inv=ACTUAL_A_CODE#rsvp`.

- [ ] Open each link signed OUT of Google (private window), on both phone and laptop.
  No Google sign-in or permission page should be needed.
- [ ] Names are prefilled and cannot be added/edited. Family sees tea 5.30 pm and
  dinner; Friends has no tea form. Both show seats 6.30 pm and fun 9 pm.
- [ ] Try saving with one unanswered guest/event. It must ask for that answer,
  not claim success or add a saved reply.
- [ ] Submit mixed Yes/No answers with independent tea/dinner answers and a
  dietary note. Confirm the saved summary, Singapore timestamp and response tab.
- [ ] Verify H-K in Guestlist are STILL unchanged. Website replies are NOT copied
  into manual column J; record those manually when you choose.
- [ ] Reopen the same link on another device. The saved answers are prefilled.
  Edit and save, then reload the first device to see the latest version.
- [ ] Open the same link in two windows. Save in one, then try saving the older
  form. It should ask to reload instead of overwriting the newer reply.
- [ ] Turn off the network before saving. No success claim; answers remain in
  the open form. Reconnect and retry. One reply, not duplicate visible guests.
- [ ] Add a fictional guest to an existing B group. Existing A stays. Reopening
  shows the added guest with no invented prior answer; stale open forms reload.
- [ ] Set a fictional guest G = No. Only their A/B clear. The group's other guests
  remain invited. A website decline must NOT itself clear G, A or B.
- [ ] Set all trial guests G = No, run Update invitation codes, then confirm those
  trial links no longer resolve. Keep/archive their rows rather than reuse groups.
  Old fictional snapshots remain in the hidden backing log, not current replies.

## Guest Experience

- [ ] Check the envelope and personalised greeting, scratch hearts, countdown,
  click hearts, moving photo strips and outfit controls on phone and laptop.
- [ ] FAQ and directions make sense for each audience. Arrival from 6 pm,
  seats by 6.30 pm; Family tea starts 5.30 pm. Verify venue and deadline yourself.
- [ ] Finalise wording that still promises later confirmation, especially the
  dress-code FAQ's "we'll confirm closer to the day", before sending invitations.
- [ ] Saved-reply/calendar controls work; messages are readable on a narrow phone.
- [ ] Test invalid link and no-code public page. Neither should expose a guest list
  or show a form for unnamed guests.
- [ ] Replace the directions QR image before guests need it and scan the actual
  published image on a second phone. Unavailable QR has an honest placeholder.
- [ ] Send a trial invitation privately to each other in the messaging app you
  will use, open the in-app link and complete a fictional RSVP there too.
- [ ] Take a fresh private workbook backup. Record the current script/deployment
  and Pages version. Send real invitations only after all relevant checks pass.

## After Launch

Use B/G and manual H-K for normal management, not script changes. Replies can be
updated at the same link, including after the deadline; guests are asked to contact
you directly for late changes. Never reuse an old group for an unrelated household,
replace a person's row with another person, delete the code register, or delete/
sort the hidden response log. For a future QR update keep its existing filename.
